## 4. PASO 4: migración Flyway (sin comentarios dentro del .sql)

**Por qué la explicación está aquí y no en el archivo:** Flyway guarda un checksum de cada migración ya ejecutada. Si editas el `.sql` (aunque sea un comentario), el servicio no arranca: `Migration checksum mismatch`. **Un SQL ya ejecutado no se edita.** Si te equivocas: crea `V2__arreglo.sql` con un `ALTER TABLE`, o en práctica borra la BD (`down -v`, **borra los datos**).

Nombre exacto: `V1__crear_<recursos>.sql` (V mayúscula, **dos** guiones bajos). En `src/main/resources/db/migration/`.

**Usa el script que trae el examen.** Plantilla de la variante 4:
```sql
CREATE TABLE notificaciones (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    referencia    VARCHAR(40)  NOT NULL,
    destinatario  VARCHAR(120) NOT NULL,
    canal         VARCHAR(20)  NOT NULL,
    mensaje       VARCHAR(255) NOT NULL,
    estado        VARCHAR(20)  NOT NULL,
    creado_en     TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_notificaciones_referencia UNIQUE (referencia)
);
```
- `CONSTRAINT uk_<recursos>_<campo> UNIQUE (<campo>)` = segunda defensa de idempotencia. **No olvidarlo.**
- Verificar (después de arrancar el servicio): `\dt` muestra `<recursos>` y `flyway_schema_history`.

### Mensaje duplicado desde Kafka UI (idempotencia)
Kafka UI → Topics → `notificacion-eventos` → **Produce Message**
- **Key:** `NOT-001`
- **Value:**
```json
{"tipo":"notificacion.solicitada","referencia":"NOT-001","destinatario":"ana@correo.com","canal":"EMAIL","mensaje":"Tu pedido salio"}
```
- Headers: vacío → **Produce Message**.
- Resultado: el topic tiene un mensaje más, la tabla **sigue con 1 fila** de `NOT-001`, el log dice `Duplicado ignorado: NOT-001`.

### Preguntas teóricas probables
- **¿Qué pasa con un mensaje repetido en Kafka?** Kafka no deduplica: lo guarda con otro offset y lo vuelve a entregar (at-least-once). La deduplicación es del consumer (consumer idempotente): `existsBy` + UNIQUE.
- **¿Por qué la referencia como key?** Misma key → misma partición → orden garantizado para esa referencia.
- **¿Para qué ErrorHandlingDeserializer?** Si llega un JSON roto (poison pill), sin él el consumer reintenta para siempre y se traba; con él se loguea y se salta.
- **¿Por qué 202 y no 201?** Porque el POST no crea nada todavía: solo acepta la solicitud y la procesa de forma asíncrona.
- **¿Qué es la compensación?** La acción que deshace o marca como fallido un paso de la saga (aquí: CANCELADA + evento `.fallida`).
- **¿Por qué el filtro por `tipo` en el consumer?** El consumer escucha el mismo topic donde publica `.enviada` y `.fallida`; sin el filtro los reprocesaría.
- **¿Por qué `auto-offset-reset: earliest`?** Un grupo nuevo lee desde el principio y no pierde los mensajes publicados antes de arrancar.
- **¿`NotificacionEvento` es una entity?** No. La entity es una fila de la tabla; el evento es el mensaje de Kafka (con `tipo`, sin `id` ni `estado`).
